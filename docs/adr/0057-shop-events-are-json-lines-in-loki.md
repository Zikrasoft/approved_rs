# Shop events are JSON lines in a Loki on the shop's own VPS

The owner wants two things from logs: to see why a problem happened, and once a week to hand a usage log to Claude to decide what to improve. Before this, the shop's log was Medusa's free-text `logger` lines plus morgan's request lines (client IP and full URL, query included), and carlab.rs on Vercel's Hobby plan has no Log Drains, so its server-side facts reached nobody.

We log **Events**: one JSON line per meaningful fact, with a stable `event` name, an `outcome`, a `reason` code and, on a request, a `request_id`. The vocabulary is one typed module, `apps/auto-service-shop/src/lib/log-event.ts`; nothing else writes an Event, and a field outside the vocabulary does not compile. The shop logs `store.request` (route pattern, status, duration, client), `store.error` (every 5xx, with its cause), `search` (intent, result count, zero-result flag), `vin.lookup` (resolved or why not), `order.handoff` (an order or a cancel handed to the lead route, delivered or why not) and `catalogue.run` (every import, publish, deletion, merge and rename, from the one place they all finish).

carlab.rs sends its own Events: its search, cart, checkout, lead and CSP-report routes post one compact Event per request to the shop's `POST /hooks/storefront-events`, which logs it under the same vocabulary. The wire schema lives in `@podbor/catalog-contract/events`, so both sides agree on it; the route takes a narrow Bearer secret (`SHOP_EVENTS_SECRET`, with `_PREVIOUS` for rotation), is rate limited and size capped, and strips any key the schema does not name. A send is fire and forget through `waitUntil` with a short timeout and never fails the visitor's request. Both sides carry Vercel's `x-vercel-id` as the request id, so a storefront Event and the shop calls it made share one id. Page flow stays in GA4 and Metrika: only server-side facts are logged.

**No personal data, by construction.** No Event field can hold a phone, a name, a Telegram handle, an email or an IP. The client is an HMAC of its address's network (the /64 for IPv6, as the rate limit counts it), keyed by `COOKIE_SECRET`, 12 hex characters: stable enough to count returning visitors, useless without the server's secret. A VIN is logged as its WMI (the maker prefix), the decoded make and a 12-character HMAC, never in full: a plain hash of a VIN can be brute forced from its model prefix. A search's text is logged, since the zero-result queries are the most useful thing in the log, but never when it contains a VIN, an `@` or a valid phone number; then `query` is `null`. Morgan's request line is switched off (`LOG_LEVEL=info` in compose), since `store.request` replaces it without the IP and the query string.

**Grafana, Loki and Alloy run beside the shop**, pinned, on an internal `logs` network. Alloy reads the Docker json-file logs from disk (no Docker socket in a container), keeps the medusa service's lines, drops any http-level line, and caps the rate at 10 lines a second (bursts of 2000), which with Loki's 30-day retention bounds the disk. Grafana listens on `127.0.0.1` only and is reached by SSH tunnel. We chose Alloy over the Loki Docker driver because the driver is a host plugin that blocks container start and stop when Loki is down; Promtail is end of life.

**The weekly export** is `infra/auto-service-shop/logs-export.sh`: it reads the last 7 days of Events (lines with an `event` label only, never Medusa's free text) through `logcli`, and writes one gzipped JSONL file and a per-event summary for the owner to hand over.

Consequences: Medusa's own error lines still reach Loki, but not the export. `COOKIE_SECRET` rotation changes every client and VIN hash. A storefront Event lost to a network failure is gone; the shop's own Events are the reliable record.
