# Part Demand is counted per number per day in the shop

The owner wants to know which parts people want before the shop opens for sales, and the catalogue should use that to order itself. Part pages are prerendered, so a visit to one reaches no server, and the shop is closed (no prices, no stock), so orders are rare. What does reach a server is an inquiry, a placed order, and a pick in the search suggestions.

We count **Demand** in a shop module, `demand`, that owns three tables and nothing else: `part_demand_day` (one row per part identifier per UTC day, with `inquiries`, `orders` and `picks`), `missed_query` (one row per redacted query per day that found nothing) and `demand_receipt` (keys of events already counted). Row ids are the natural keys (`<identifier>|<day>`, `<day>|<query>`), so every increment is one `insert ... on conflict (id) do update`, safe under concurrent writers. A keyed signal (an order by its id, a storefront event by its Vercel request id) is counted once even when it is delivered twice. The daily job `refresh-part-demand` deletes everything older than 120 days, which keeps the 90-day report whole and bounds the tables. Nothing in them names a person: identifiers, counts, and queries that already passed `loggedQuery` (no VIN, email or phone).

**Signals.** An inquiry: the parts-list form posts each listed part's page slug as `demand_parts`, and carlab.rs's `/api/leads` sends one `storefront.demand` event when it accepts the form (a 302 that the honeypot did not cause). An order: the `order.placed` subscriber counts each part line, never an add-on line. A pick: the search box beacons the picked suggestion's slug to `/api/part-pick`, which forwards it; the beacon carries no identifier and sets nothing, so it needs no consent. A visit to a part page from search results is **not** counted: it would need a beacon on every result link or a redirect through a function, and a page view is a much weaker signal than the three above. The shop resolves a slug to an identifier by splitting at its last dash, since a normalized number never holds one, and logs the count of slugs and matches, never the slugs.

**Score and thresholds** live in `src/modules/demand/ranking.ts`, one place for both the sort and the badges: over the last 30 days an order weighs 5, an inquiry 3, a pick 1. A number is **popular** from 2 orders plus inquiries on (picks alone never make it popular, since anyone can fake them with curl). A popular number is a **top** number when it is among the 3 most demanded popular numbers of its Category. The shop sends `demand: { score, popular, top }` on part pages and search results (`.nullable().default(null)`, null for no demand), and writes the score into the search document as `demand`.

**Sort.** `GET /store/search?sort=popular` ranks by `demand` first and keeps the default order behind it, so with no demand the order is exactly the default one. Typesense takes three sort fields, so a query that matched a car keeps the fitting-car rank first and loses the standing tie-break. The storefront offers «Популярные» only on listings without a typed query, where relevance does not lead; the prerendered category pages link to the search page with `sort=popular`, which keeps the sort through filters, pages and the filter reset, and redirects a sort it does not know, or one beside a query, away. The index score is refreshed by the daily job, which reindexes every number with demand in the last 31 days (the 31st day drops out of the window).

**Storefront.** The «Часто заказывают» block (the hub, a category, a Model and a Vehicle page), the «Часто берут» badge on part rows, and the hub's category order are computed at build from the snapshot's `demand`. The block needs 2 popular parts and shows at most 6. These are as fresh as the last storefront build, which follows a Publish; the shop's own search results and sort are fresh within a day.

**Report.** The admin «Спрос» page reads `GET /admin/demand?days=7|30|90`: numbers, Categories and Models (from the fitments of demanded parts) by weighted demand with the breakdown, and the queries that found nothing. The weekly Loki export adds what the tables do not keep: the `storefront.demand` events with how many slugs matched, the `search` events with their intent and result counts, so the owner can see how much of the demand never matched the catalogue.

Consequences: the suggestion pick is the cheapest signal to fake, so it weighs least and never makes a part popular. A zero-result query typed into the suggestion box is counted per debounced request, so a slow typist can count one query more than once; the report groups by query, which keeps it readable. A canceled order still counts as demand: the visitor wanted the part.
