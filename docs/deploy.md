# Деплой: три сайта на Vercel, бэкенд магазина на VPS

## Стек

- **Astro v7** — статические сайты, отдельные роуты опционально на SSR
  (`export const prerender = false`)
- **pnpm v11 + Turborepo** — монорепо, приложения в `apps/*`, общие пакеты в
  `packages/*`
- **Vercel** — хостинг. Три отдельных проекта, по одному на приложение
- **GitHub Actions** — единственное место, где реально идёт сборка и деплой
  (`.github/workflows/ci.yml`)

## Три сайта — один репозиторий

| Приложение          | Домен         | Бренд                    | Что деплоит                                                                                 |
| ------------------- | ------------- | ------------------------ | ------------------------------------------------------------------------------------------- |
| `apps/approved-rs`  | `approved.rs` | Approved.rs — автоподбор | сайт + `/api/leads`, `/api/contact-click`, `/api/telegram-webhook`, `/api/reminders` (cron) |
| `apps/auto-service` | `carlab.rs`   | CarLab — автосервис      | сайт + `/api/leads`, `/api/contact-click`                                                   |
| `apps/detailing`    | `details.rs`  | Details — детейлинг      | сайт + `/api/leads`, `/api/contact-click`                                                   |

Каждое приложение владеет своим `astro.config.mjs`, `vercel.json`,
`keystatic.config.ts` и `.env*`. Vercel CLI определяет проект по рабочей
директории, поэтому каждая деплой-джоба целиком выполняется из своей
`apps/<app>`.

**Один бот, один чат, одно хранилище заявок, три бренда.** Telegram позволяет
ровно один webhook URL на бота, поэтому `api/telegram-webhook.ts` и
`api/reminders.ts` живут только в `apps/approved-rs`. Все три приложения пишут
в один и тот же `data/leads.json` в одном Vercel Blob store и разделяются полем
`brand` у заявки — его проставляет сервер (`createNotifyLead({ brand })`),
посетитель задать его не может.

> Пути без префикса в этом документе — относительно приложения, о котором идёт
> речь (`vercel.json` в разделе про approved.rs = `apps/approved-rs/vercel.json`).
> В корне репозитория лежат только `.github/`, конфиги линтеров, `pnpm-lock.yaml`
> и «пустой» `vercel.json` с одним `git.deploymentEnabled: false`.

> Переименование в CarLab / Details завершено: старых плейсхолдеров в коде не
> осталось. Единственные вхождения `PRIZMA` / `AutoHub` — фикстуры в тестах
> `packages/lead-crm`, где бренд это произвольная строка.

## Как устроен деплой

### Vercel ничего не собирает

`git.deploymentEnabled: false` (корневой `vercel.json`, продублировано в
`apps/approved-rs/vercel.json`) отключает собственный git-триггер Vercel.
Git-интеграция читает конфиг из корня репозитория, а не из директории
приложения, — поэтому файл в корне и существует, только ради этой строчки.
Без неё каждый пуш в любую ветку запускал бы падающий preview-билд.

Собирает и деплоит GitHub Actions — и только те сайты, которые отстали от
`main` (см. «Деплоится не всё подряд» ниже):

- джоба `deploy` — `apps/approved-rs`;
- джоба `deploy-brand-site` — матрица из `detailing` и `auto-service`.

Обе делают одно и то же из своей директории приложения:

```bash
pnpm exec vercel pull --yes --environment=production
pnpm exec vercel build --prod
pnpm exec vercel deploy --prebuilt --prod --archive=tgz
```

…а последним шагом (`Record what is live`) передвигают свой тег
`refs/tags/deployed/<app>` на только что выложенный SHA. Из него следующий
прогон и узнаёт, что уже лежит в проде.

Проект в Vercel нужен только чтобы хранить переменные окружения, домен и быть
целью деплоя. Настройки сборки в дашборде значения не имеют — они уже
зафиксированы в `vercel.json` каждого приложения:

```json
{
  "framework": "astro",
  "buildCommand": "pnpm run build",
  "installCommand": "pnpm install",
  "outputDirectory": "dist"
}
```

Раньше сборку делал сам Vercel через git-интеграцию (`ignoreCommand`,
`scripts/vercel-ignore-build.sh`) — но так проверки гонялись дважды (в GitHub
Actions и заново в контейнере Vercel), и несовпадение версии pnpm между ними
однажды привело к тому, что реальные деплои с новым контентом молча
пропускались («Canceled by Ignored Build Step», без явной ошибки). Теперь
проверка ровно одна, и деплоится именно тот коммит, который её прошёл.

### Порядок джоб

`check` (lint/prettier/typecheck/test, sh-тесты скриптов, shellcheck,
actionlint) → `translate` → `verify`; параллельно с ними
`medusa-integration` (HTTP-тесты Medusa на postgres+redis из `services:`),
которого ждёт только `medusa-image`. Дальше `medusa-image` → `deploy-medusa`
→ `record-medusa` (двигает тег), `deploy` (approved.rs) и `deploy-brand-site`:
оба сайтовых деплоя ждут `deploy-medusa` и не стартуют, только если она упала
(пропущенная `deploy-medusa` их не держит) — иначе упавший VPS выкатил бы
approved.rs без двух других сайтов и развёл бы схему лидов в `data/leads.json`.
`deploy*` запускаются только на `main`, каждая только если предыдущая прошла.
Воркфлоу срабатывает на пуш в любую **ветку** и никогда на тег: фильтр по
тегам без фильтра по веткам выключил бы ветки совсем, а на чекауте тега `translate` оказался бы на detached HEAD и не смог бы запушить.

`translate` идёт до деплоя, а не параллельно ему: скрипты перевода
отрабатывают, коммит с переводами уходит в ту же ветку, и всё, что дальше,
чекаутит именно тот SHA, который остался после неё
(`needs.translate.outputs.sha`). Если переводить было нечего, SHA — исходный
коммит пуша. Так в прод физически не может уехать контент без переводов.
`verify` перепрогоняет тесты уже на этом SHA: `translate` пушит под
`GITHUB_TOKEN`, а такой пуш не запускает новый прогон — иначе переведённое
дерево не проверял бы никто.

### Деплоится не всё подряд

Пуш в `main` больше не выкатывает все три сайта. Шаг `scope` в джобе `verify`
собирает список приложений, устаревших в проде, и обе деплой-джобы читают его
через `needs.verify.outputs.changed`.

База сравнения — **не предыдущий коммит, а тег `refs/tags/deployed/<app>`**,
который каждая деплой-джоба передвигает на выложенный SHA. Разница
принципиальна: `github.event.before` отвечает на вопрос «что изменилось в этом
пуше», а нужен ответ на «что сейчас лежит в проде». Приложение, у которого
деплой упал и которое с тех пор не менялось, в дифф с предыдущим коммитом не
попадёт никогда — и останется устаревшим до первой случайной правки в своей
директории. С тегом оно попадает в список на каждом следующем пуше, пока
деплой не пройдёт: тег двигает только успешный деплой.

Список собирается по каждой `apps/*/` так:

| Что видит `scope`                                                                           | Решение                 |
| ------------------------------------------------------------------------------------------- | ----------------------- |
| тега `deployed/<app>` ещё нет                                                               | деплоим                 |
| тег не предок `HEAD` (force-push, откат ветки)                                              | деплоим                 |
| изменились корневые файлы сборки (список ниже)                                              | деплоим                 |
| `turbo --filter="...[<тег>]"` называет пакет изменившимся                                   | деплоим                 |
| turbo упал или его вывод не разобрался                                                      | деплоим                 |
| `apps/medusa`: изменилось что-то в `infra/medusa/`                                          | деплоим                 |
| `auto-service`: `catalog-version.txt` сайта ≠ версия каталога в Medusa, или её не прочитать | деплоим                 |
| `auto-service`: сайт отвечает 404 на `catalog-version.txt` или `disabled`                   | эта проверка не деплоит |
| turbo положительно сказал, что пакета среди изменившихся нет                                | пропускаем              |

**`infra/medusa/` проверяется отдельно**, как и корневые файлы: turbo знает
только пакеты воркспейса и приписывает всё остальное `//`, поэтому правка
Dockerfile, compose, Caddyfile или скриптов без этой строки не выкатила бы
бэкенд никогда.

**Каталог магазина — отдельная причина выкатить carlab.rs.** Цены и товары
запекаются в статику, поэтому правка каталога в админке Medusa должна
пересобрать сайт, даже если код не менялся. Medusa после правки дёргает
`workflow_dispatch` у `ci.yml` (`GITHUB_DISPATCH_TOKEN`), а шаг `scope`
сравнивает `https://carlab.rs/catalog-version.txt` (версия, с которой сайт
собран) с `GET $MEDUSA_URL/store/catalog-version` через
`.github/scripts/catalog-stale.sh`. Скрипт отвечает «не деплоить» ровно в
трёх случаях: версии равны; сайт отвечает `disabled` (магазин выключен); сайт
отвечает 404 — файла ещё нет, магазин не запущен (Plan 4 его создаст). Всё
остальное — сеть, 5xx, нет `MEDUSA_URL`/`MEDUSA_PUBLISHABLE_KEY`, Medusa
отвечает не JSON, `unstamped` (каталог ни разу не штамповался) — «деплоить»:
неизвестность, как и везде в `scope`, отвечает лишним деплоем, а не
пропущенным. Тесты на все ветки — `.github/scripts/catalog-stale.test.sh`.

**Любая неизвестность отвечает «деплоить».** Единственный ответ «нет» — когда
turbo прямо перечислил изменившиеся пакеты и приложения в списке не оказалось.
Цена ошибки в эту сторону — лишний деплой; в обратную — прод, молча оставшийся
на старом коммите при зелёном CI.

**Фильтр `...[<тег>]` — с ведущими точками, и это не опечатка.** Точки
добавляют к изменившемуся пакету всех, кто от него зависит. Поэтому правка в
`packages/lead-crm` или `packages/i18n` выкатывает сразу все три сайта, а не
только тот, который трогали в том же пуше. Это единственное, что не даёт двум
версиям схемы заявки встретиться в общем `data/leads.json`: все три сайта
пишут в один файл, и выложенный наполовину пакет означает, что один сайт пишет
записи, которых другой уже (или ещё) не понимает — а нечитаемые записи уезжают
в `data/leads-unreadable.json` и разбираются руками. Инвариант не держит больше
ничто: ни тест, ни схема половинчатый выкат не замечают. Сужать фильтр до
директорий приложений нельзя.

**Корневые файлы проверяются отдельным `git diff`.** turbo приписывает
изменения в корне репозитория пакету `//`, а не приложениям, поэтому бамп
зависимости в фильтр `...[тег]` не попал бы вообще и не выкатил бы ничего.
Шаг `scope` смотрит на них сам:

```
pnpm-lock.yaml  pnpm-workspace.yaml  turbo.json  package.json
.npmrc  .node-version  .pnpmfile.cjs  .github/actions/setup-pnpm/action.yml
```

Любое изменение в них выкатывает каждое приложение, чей тег `deployed/*`
старше этого изменения. Список ведётся руками — появится новый файл, влияющий
на сборку, добавить его надо туда же. Остальной `.github/` намеренно не
отслеживается: иначе любая правка воркфлоу выкатывала бы все три сайта.

Включая `apps/medusa`: бамп Astro пересоберёт и смигрирует бэкенд, бамп
Medusa передеплоит три сайта. Так решено осознанно (Plan 3): lockfile один на
всех, приписать его изменение одному приложению `scope` не может, а лишний
деплой дешевле ошибки в эту сторону. По той же логике `setup-pnpm` ставит
весь воркспейс (включая ~680 MB Medusa) в каждой джобе — пока это не мешает
измеримо, `pnpm install --filter` не вводим.

### Теги `deployed/*`

`refs/tags/deployed/approved-rs`, `deployed/detailing`,
`deployed/auto-service` и `deployed/medusa` появляются и двигаются сами:
последний шаг каждой деплой-джобы переставляет свой тег на выложенный SHA
через `gh api` (`PATCH` с `force`, а если тега ещё нет — `POST`).

Это **служебные теги, а не релизные**. Версий они не обозначают, в release
notes не участвуют, читает их ровно один шаг `scope`.

- **Удалить такой тег — не авария.** Следующий прогон не найдёт его, ответит
  «деплоим» и заведёт тег заново. Цена — один лишний деплой, и только один.
- **Удаление — и есть штатный способ передеплоить один сайт:**

  ```bash
  git push origin :refs/tags/deployed/detailing
  # затем Actions → CI → Run workflow на main
  ```

- **Передвигать тег руками вперёд — наоборот, опасно.** Это сообщает CI, что в
  проде лежит коммит, которого там нет, и следующий пуш деплой пропустит.
  Сомневаетесь — удаляйте, а не переставляйте.

Если передеплоить надо всё и сразу — Actions → CI → Run workflow, галочка
**Deploy every app, whatever the tags say**. Она нужна, когда изменилось что-то
вне git: переменная окружения или настройка проекта в дашборде Vercel, ротация
Blob-хранилища. Такие правки требуют пересборки, но в истории репозитория следа
не оставляют, а `scope` смотрит только в git.

Всё это один воркфлоу и один прогон. Раньше перевод жил отдельным файлом
(`translate.yml`), а `ci.yml` ждал его завершения через `workflow_run` —
и решал джобой `gate`, деплоить сейчас или отложить до после-переводного
прогона. `gate` отвечал на вопрос «тронул ли пуш контент?» по списку файлов
из push-payload, а `paths:`-фильтр второго воркфлоу — по реальному диффу;
на мерж-коммитах эти два ответа расходились, и `main` деплоился дважды.

**Почему сейчас это не повторится.** Та история выглядит ровно как возражение
против нынешней схемы: «мы уже пробовали деплоить не всё подряд, и `main`
выкатился дважды». Но ломалась там не фильтрация, а два независимых ответа на
один вопрос. `gate` разбирал `jq`-ом массив `commits` из push-payload, а
`paths:` второго воркфлоу смотрел на настоящий дифф; GitHub на мерж-коммитах
присылает `commits: null` — payload врал, дифф нет, ответы расходились
(коммиты `b77293e` и `928417f` — обе попытки починить это на стороне `jq`).
Сейчас ответ ровно один, его даёт шаг `scope` в `verify`, и считается он не по
payload, а по реальной истории git внутри уже сделанного чекаута: `git diff` и
`turbo` против тега `deployed/*`. Мерж-коммит для них — обычный коммит.

`environment: production` в деплой-джобах — обычный GitHub Environment,
создаётся сам при первом запуске, без правил защиты.

### Следствие: переменные окружения живут в проекте Vercel

`vercel pull` скачивает переменные production-окружения проекта в
`.vercel/.env.production.local`, и `vercel build` собирает уже с ними. То есть:

- **переменные задаются в дашборде Vercel, а не в секретах GitHub.** В GitHub
  лежат только токен/ID для доступа к Vercel и `OPENAI_API_KEY` (см. ниже);
- **отсутствие переменной не ломает сборку.** `PUBLIC_*` инлайнятся в HTML на
  этапе билда, и незаданная переменная без фолбэка превращается в
  `undefined` прямо в разметке (`https://t.me/undefined`). Серверные
  переменные проверяются в рантайме и роняют роут в 500 уже в проде;
- **изменение переменной применяется только после нового деплоя** — старая
  сборка уже содержит старое значение внутри HTML.

Задаются в Vercel Dashboard → нужный проект → Settings → Environment Variables
(окружение Production; Preview не используется — preview-деплоев нет).

`PUBLIC_*` доступны в браузере — секреты туда не класть.

### Аналитика — переменных окружения нет

Счётчики зашиты в каждый `src/utils/constants.ts` и никогда не читаются из
env: они не секреты, публично видны в любом запросе с сайта, и разнести их по
трём дашбордам Vercel значит завести третье место, где можно ошибиться.

| Сайт        | Яндекс.Метрика |
| ----------- | -------------- |
| approved.rs | `111800377`    |
| carlab.rs   | `112647692`    |
| details.rs  | `112647721`    |

У каждого домена свой счётчик; переиспользовать чужой нельзя. Google Analytics
снят со всех трёх — 167 КиБ gtag.js целиком ушли из бандла.

Все три ведут себя одинаково: хит уходит в очередь `ym` при первой загрузке
страницы, а сам `tag.js` докачивается уже после `load`, в простое браузера —
из критического пути он убран, но ни один просмотр из-за этого не теряется.
Явный отказ в баннере действует со следующей загрузки — выгрузить уже
запущенный счётчик Метрики нечем. Метрика инициализируется с `webvisor: true`,
то есть пишет сессии; форма заявки из записи исключена классами
`ym-hide-content ym-disable-keys` на `LeadForm.astro` во всех трёх
приложениях.

**Если меняете счётчик или включаете аналитику там, где её не было**, вместе с
ним идут три вещи: русский раздел `privacy` в `src/content/i18n/pages.yaml`,
строка `cookie.notice` в `site.yaml`/`dictionary.yaml` и `COOKIE_POLICY_VERSION`
в `src/utils/constants.ts`. Без поднятия версии у всех, кто уже ответил на
баннер, согласие молча начнёт означать другое.

У approved.rs в `src/utils/constants.ts` стоит `!` без фолбэка — незаданная
переменная даёт `undefined` в вёрстке. У carlab.rs и details.rs есть фолбэки
на номера-заглушки: сайт не сломается, но будет показывать неправильный
контакт — это хуже, чем битая ссылка, потому что незаметно.

`PUBLIC_WHATSAPP_NUMBER` у approved.rs заодно служит номером для обычного
звонка (`PHONE_NUMBER` там алиас на неё).

| `TELEGRAM_BOT_TOKEN`      | ✅          | ✅        | ✅         | `/api/leads` и `/api/contact-click` отвечают 500                 |
| `TELEGRAM_BOT_USERNAME`   | ✅          | ✅        | ✅         | то же — 500                                                      |
| `TELEGRAM_GROUP_ID`       | ✅          | ✅        | ✅         | то же — 500                                                      |
| `TELEGRAM_OWNER_ID`       | ✅          | ✅        | ✅         | заявки этого бренда не приходят владельцу в личку                |
| `TELEGRAM_ADMIN_ID`       | ✅          | ✅        | ✅         | заявки этого бренда не приходят админу в личку                   |
| `TELEGRAM_WEBHOOK_SECRET` | ✅          | —         | —          | `/api/telegram-webhook` отвечает 401 на всё — кнопки бота мертвы |

> **Главная ловушка при заведении новых проектов.** Все три `src/lib/crmBot.ts`
> вызывают `requireEnv('TELEGRAM_BOT_TOKEN')`, `requireEnv('TELEGRAM_BOT_USERNAME')`
> и `requireEnv('TELEGRAM_GROUP_ID')` на верхнем уровне модуля. Роуты
> `/api/leads` и `/api/contact-click` — `prerender = false`, поэтому **сборка
> проходит успешно**, а падает уже первый реальный запрос в проде. Легко
> выкатить «зелёный» деплой с нерабочей формой.

`TELEGRAM_OWNER_ID` / `TELEGRAM_ADMIN_ID` — числовые Telegram user id (не
`@username`, взять у [@userinfobot](https://t.me/userinfobot)), через запятую
если у человека несколько аккаунтов (`111,222`). Отсутствие не роняет роут —
просто личные сообщения по заявкам этого бренда никуда не уходят. Ставить во
всех трёх проектах одни и те же id.

Бот один на все бренды: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и
`TELEGRAM_GROUP_ID` во всех трёх проектах одинаковые.

### `SITE`

Отдельная история: в дашборде её задавать не нужно.

- URL сайта захардкожен как `site:` в `astro.config.mjs` каждого приложения, и
  именно оттуда Astro наполняет `import.meta.env.SITE`, которую читает
  `src/utils/constants.ts`. Переменная окружения `SITE` на это значение не
  влияет — Astro инлайнит в `import.meta.env` только `PUBLIC_*` и собственные
  встроенные ключи;
- `vercel.json` каждого приложения дополнительно кладёт `env.SITE` в рантайм
  функций — на случай, если он кому-то понадобится;
- реально `process.env.SITE` читает только локальный скрипт
  `scripts/register-webhook.ts` (из `.env.local`).

Меняется домен → правится `site:` в `astro.config.mjs` и `env.SITE` в
`vercel.json`, а не переменная в дашборде.

## Общий Blob store на три проекта

Все три приложения создают хранилище одинаково:

```ts
createVercelBlobStorage({ path: 'data/leads.json' });
```

Один и тот же ключ. Значит, чтобы заявки всех брендов лежали в одном файле —
а они должны, потому что бот и cron живут только в approved.rs и обязаны
видеть заявки всех трёх брендов — **store должен быть один, подключённый ко
всем трём проектам**.

1. Vercel Dashboard → Storage → Create → Blob (один раз, не по одному на проект)
2. У созданного store → Connect Project → подключить все три проекта
3. В каждом проекте после этого сам появится `BLOB_READ_WRITE_TOKEN`,
   указывающий на этот же store

Никогда не задавать `BLOB_READ_WRITE_TOKEN` руками: значение, скопированное
из другого проекта, легко разъедет со store, и часть заявок уедет в файл,
которого бот не видит.

Разделение по брендам — поле `brand` у заявки (`Approved.rs` / `CarLab` /
`Details`), проставляется сервером. Отдельного файла на бренд нет.

Второй файл в том же store всё-таки бывает: `data/leads-unreadable.json`.
Туда копируются записи, которые перестала принимать схема, — например после
её изменения. Появляется сам, когда такая запись встретилась; админу при
этом приходит сообщение в Telegram с количеством и именем сайта, который её
нашёл. Из `data/leads.json` при этом **ничего не удаляется**: записи остаются
на месте, пока их не разберут руками. Автоматически из блоба не исчезает
ничего.

## Keystatic: три GitHub App'а

Все три `keystatic.config.ts` в проде ходят в один и тот же репозиторий
(`storage: { kind: 'github', repo: 'Zikrasoft/approved_rs' }`) и различаются
только префиксом пути (`APP_ROOT = 'apps/<app>/'`). Но OAuth-callback у
GitHub App фиксированный и привязан к домену:

```
https://<домен>/api/keystatic/github/oauth/callback
```

Три домена — три отдельных GitHub App'а, каждый установлен на тот же
репозиторий `Zikrasoft/approved_rs`.

Для каждого:

1. GitHub → Settings → Developer settings → GitHub Apps → New GitHub App
2. Callback URL — как выше, с доменом соответствующего сайта
3. Права: Repository permissions → Contents: Read and write
4. Install App → на репозиторий `Zikrasoft/approved_rs`
5. Сгенерировать client secret
6. В соответствующий проект Vercel положить `KEYSTATIC_GITHUB_CLIENT_ID`,
   `KEYSTATIC_GITHUB_CLIENT_SECRET`, `PUBLIC_KEYSTATIC_GITHUB_APP_SLUG` (slug
   из URL приложения) и свой случайный `KEYSTATIC_SECRET`

Локальная разработка через GitHub App не ходит: `import.meta.env.PROD` там
`false`, и Keystatic пишет прямо в рабочую копию (`storage: { kind: 'local' }`).

`PUBLIC_KEYSTATIC_GITHUB_APP_SLUG` нельзя помечать в Vercel как Sensitive:
такие переменные недоступны на сборке, а slug нужен клиентскому бандлу
`/keystatic`. Три секрета — наоборот, Sensitive, их читает только функция.

Сайт без этих переменных собирается, деплоится и отдаёт все страницы; мёртв
только вход в `/keystatic`, и только когда кто-то в него полезет — carlab.rs и
details.rs прожили так двенадцать дней. Проверять руками:
`curl -o /dev/null -w '%{http_code}' https://<домен>/api/keystatic/github/login`
— должно быть 307, а не 500.

| -------------------------------- | ---------------------------------------- | ---------------------------------------------------------------- |
| `OPENAI_API_KEY`                 | джоба `translate` (автоперевод контента) | OpenAI. **Только в GitHub, на Vercel не нужен**                  |
| `VERCEL_TOKEN`                   | все деплой-джобы                         | [vercel.com/account/tokens](https://vercel.com/account/tokens)   |
| `VERCEL_ORG_ID`                  | все деплой-джобы                         | `.vercel/project.json` → `orgId` после `vercel link`             |
| `VERCEL_PROJECT_ID`              | деплой approved.rs                       | Project Settings → General нужного проекта                       |
| `VERCEL_PROJECT_ID_AUTO_SERVICE` | деплой carlab.rs                         | то же, у проекта carlab.rs                                       |
| `VERCEL_PROJECT_ID_DETAILING`    | деплой details.rs                        | то же, у проекта details.rs                                      |
| `MEDUSA_VPS_HOST`                | деплой Medusa (IPv4 сервера)             | Hetzner Console                                                  |
| `MEDUSA_VPS_USER`                | деплой Medusa                            | `deploy` (создаёт `bootstrap-host.sh`)                           |
| `MEDUSA_VPS_SSH_KEY`             | деплой Medusa (приватный ключ CI)        | `ssh-keygen -t ed25519`, публичная часть — `restrict` на сервере |
| `MEDUSA_VPS_KNOWN_HOSTS`         | деплой Medusa (ключ хоста)               | `ssh-keyscan -t ed25519 <IPv4>`, отпечаток сверить               |
| `MEDUSA_PUBLISHABLE_KEY`         | шаг `scope` (версия каталога)            | админка Medusa → Settings → Publishable API Keys                 |

`MEDUSA_VPS_*` — секреты **репозитория**, не окружения `production`: у
`medusa-image` окружения нет, и с секретами окружения он не запушил бы образ,
а `deploy-medusa` пытался бы стянуть несуществующий тег.

Плюс **переменная** (Variables, не Secrets) `MEDUSA_URL` = `https://api.carlab.rs`.
Пока `MEDUSA_VPS_*` не заданы, шаг `guard` в `deploy-medusa` пишет
«`MEDUSA_VPS_* secrets are not set — skipping the medusa deploy.`», а
`medusa-image` не пушит образ («`MEDUSA_VPS_* secrets are not set — nothing
will deploy the image, so it is not pushed.`», пушит только когда заданы все
четыре) — воркфлоу зелёный.

> **Внимание: незаданный `VERCEL_PROJECT_ID_*` не подсвечивается никак.** Шаг
> `guard` в джобе `deploy-brand-site` проверяет, что секрет непустой, и если
> он пустой — **пропускает все остальные шаги и оставляет джобу зелёной**. В
> Actions это выглядит как успешный деплой; в логе `guard` будет строчка
> «`VERCEL_PROJECT_ID_… is not set — skipping the … deploy`». Единственный
> способ заметить — прочитать лог или увидеть, что на сайте нет изменений.
> У approved.rs такого guard нет: без `VERCEL_PROJECT_ID` джоба `deploy`
> честно падает на `vercel pull`.
>
> Проверка живёт в шаге, а не в `if:` джобы, потому что контекст `matrix` в
> условии уровня джобы недоступен.
>
> С появлением тегов `deployed/*` у `guard` есть и вторая причина пропустить
> деплой, уже штатная: «`<app> is current in production — skipping`» — сайт не
> менялся с прошлого выката. Это нормальная работа, а не сломанная
> конфигурация. Различать по тексту в логе шага `guard`: «is not set» — ошибка
> настройки, «is current in production» — так и задумано.

### Права джоб (`permissions`)

`GITHUB_TOKEN` выдаётся по джобам, а не на весь файл. `contents: write` держат
четыре джобы, и по двум разным поводам:

| Джоба                | `permissions`                       | Зачем именно столько                                                                        |
| -------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------- |
| `check`              | `contents: read`                    | только чекаут                                                                               |
| `translate`          | `contents: write`                   | коммитит и пушит переводы в ту же ветку                                                     |
| `verify`             | `contents: read`                    | чекаут с `fetch-depth: 0` — теги `deployed/*` приезжают вместе с историей                   |
| `medusa-integration` | `contents: read`                    | только чекаут                                                                               |
| `medusa-image`       | `contents: read`, `packages: write` | пушит `ghcr.io/zikrasoft/podbor-medusa:<sha>` в GHCR                                        |
| `deploy-medusa`      | `contents: read`, `packages: read`  | даёт серверу разовый токен на `docker pull`; писать в репозиторий этим токеном нельзя       |
| `record-medusa`      | `contents: write`                   | двигает `deployed/medusa` после успешного `deploy-medusa` — отдельная джоба, только за этим |
| `deploy`             | `contents: write`                   | передвигает `refs/tags/deployed/approved-rs` после успешного деплоя                         |
| `deploy-brand-site`  | `contents: write`                   | то же для `deployed/detailing` и `deployed/auto-service`                                    |

Запись у `translate` и запись у деплой-джоб — разные вещи: первая меняет
содержимое ветки, вторая трогает только служебные теги. Двигать `deployed/medusa`
вынесено в отдельную джобу `record-medusa` нарочно: `deploy-medusa` шлёт свой
`GITHUB_TOKEN` на сервер (разовый логин в GHCR), и токен с правом записи в
репозиторий там лишний — уедет на VPS токен, который умеет только читать
пакеты. Принятый риск: этот же токен несёт и `contents: read`, то есть пока
джоба жива, с сервера можно прочитать приватный репозиторий. Кроме
`contents`, воркфлоу просит только `packages` — и только в двух джобах Medusa.

Обе деплой-джобы чекаутятся с `persist-credentials: false`. Токен им нужен
только на последнем шаге, где он передаётся явно через `GH_TOKEN`, а в
промежутке `vercel build` выполняет код репозитория — оставлять ему в
`.git/config` записанный токен с правом записи незачем.

Две ловушки, обе выглядят как «сломались секреты Vercel», но к ним отношения
не имеют:

- Settings → Actions → General → Workflow permissions должно быть **Read and
  write**. При «Read repository contents» падают и `translate`, и шаг с тегом
  — с «Resource not accessible by integration».
- Tag protection rules не должны накрывать `deployed/*`. Если накроют, сайт
  выложится, а джоба покраснеет уже после этого: тег останется старым, и
  следующий прогон выкатит тот же самый сайт заново.

## Бэкенд магазина: Medusa на VPS (`api.carlab.rs`)

`apps/medusa` — не Vercel. Это docker compose на одном сервере Hetzner Cloud
(CX23: 2 vCPU x86, 4 GB; запасной вариант — CPX22), всё описано в
`infra/medusa/`:

| Файл                                     | Что это                                                                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `Dockerfile` + `Dockerfile.dockerignore` | прод-образ: пакеты через turbo, `pnpm --filter @podbor/medusa build`, `pnpm deploy --legacy`; рантайм из `.medusa/server` под `node` |
| `docker-compose.yml`                     | postgres 16.15, redis 7.4.9, medusa (образ из GHCR по sha), caddy 2.11.4                                                             |
| `caddy/Caddyfile`                        | `api.carlab.rs` → `medusa:9000`, TLS, заголовки безопасности, тело запроса до 25 MB                                                  |
| `production.env.example`                 | шаблон `/srv/carlab/.env`                                                                                                            |
| `deploy.sh`, `backup.sh`, `restore.sh`   | выкат, ночной бэкап, восстановление                                                                                                  |
| `bootstrap-host.sh`, `harden-ssh.sh`     | первичная настройка сервера (один раз, руками)                                                                                       |

### Сервер

- `/srv/carlab/` — `docker-compose.yml`, `caddy/Caddyfile` и скрипты кладёт
  CI при каждом деплое; `.env` (права 600) пишется руками один раз;
  `.previous-tag` — предыдущий выложенный sha, для отката. `deploy.sh` после
  успешного выката удаляет образы Medusa, кроме текущего и `.previous-tag`
  (ошибка удаления деплой не валит) — иначе ~650 MB на выкат забьют диск.
- `/var/backups/carlab/` — бэкапы, хранятся 7 дней; cron
  `/etc/cron.d/carlab-backup` в 03:30 UTC, лог `/var/log/carlab-backup.log`.
  Это копия на том же диске; внесерверная копия в фазе 1 — автобэкапы Hetzner.
- Наружу опубликован только Caddy: 80, 443, 443/udp. У Medusa, Postgres и
  Redis портов на хосте нет; Postgres и Redis сидят во внутренней сети без
  выхода в интернет. Это не косметика: rate-limit'ы Medusa ключуются по
  `req.ip` (IPv6 — по /64) при `trust proxy 1`, а Caddy перезаписывает
  `X-Forwarded-For` адресом клиента. Любой второй прокси или CDN перед
  Caddy сделает всех клиентов одним адресом. Проверяет
  `infra/medusa/test/compose.test.sh`.
- IPv6 доходит до Caddy напрямую: сеть `edge` двустековая (`enable_ipv6`,
  ULA `fd00:ca7:1ab::/64`), а `userland-proxy` в `daemon.json` выключен.
  Никогда не включайте userland proxy обратно — все IPv6-клиенты станут
  адресом шлюза docker и попадут в одну корзину rate-limit'а.
- Лимиты памяти на 4 GB: medusa 1536m (куча Node 1024 MB), postgres 512m,
  redis 256m, caddy 128m. В простое при проверке плана: medusa ~310–410 MiB,
  postgres ~40 MiB, redis ~6 MiB, caddy ~60 MiB. Реальные цифры под нагрузкой
  — после первого деплоя (`docker stats --no-stream`).

### `.env`

Шаблон — `infra/medusa/production.env.example`, `env.ts` проверяет всё при
старте. Неочевидное:

- `MEDUSA_TAG` руками не трогать — его переписывает `deploy.sh`.
- `POSTGRES_PASSWORD`, `JWT_SECRET`, `COOKIE_SECRET` — `openssl rand -hex 32`.
  Именно hex: compose подставляет `$…` внутри `.env`.
- `DATABASE_URL` и `REDIS_URL` в `.env` не пишутся: их собирает compose из
  имён сервисов и `POSTGRES_PASSWORD`.
- `REBUILD_ON_CATALOG_EVENTS=true` — по умолчанию `false`, и тогда правка
  каталога никогда не пересоберёт сайт.
- `SHOP_ORDER_HOOK_URL` и `SHOP_ORDER_HOOK_SECRET` — только парой; пустые,
  пока на carlab.rs нет приёмника (Plan 4).
- `GITHUB_DISPATCH_TOKEN` — fine-grained PAT только на этот репозиторий,
  Actions: Read and write.

### Как выкатывается

1. `medusa-image` собирает образ из SHA после `translate` (в образ попадает
   переведённый `emails.yaml`), мигрирует им пустую базу из `services:` и
   поднимает до `healthy`. На ветках на этом всё. На `main` — только если
   `medusa` в списке `scope` — пушит `ghcr.io/zikrasoft/podbor-medusa:<sha>`,
   и только когда заданы все четыре секрета `MEDUSA_VPS_*` — иначе шаг
   выводит предупреждение и молча завершается без пуша.
2. `deploy-medusa` кладёт стек-файлы tar'ом по ssh в `/srv/carlab`, логинит
   сервер в GHCR разовым токеном джобы, запускает `deploy.sh <sha>` и
   разлогинивает (в том числе при ошибке). Тег `deployed/medusa` эта джоба
   **не двигает** — за это отвечает следующая, `record-medusa`, с отдельным
   `contents: write`; токен, который `deploy-medusa` отправляет на сервер,
   писать в репозиторий не умеет.
3. `deploy.sh`: отказ без `.env` и для всего, что не 40-символьный sha;
   `pull` образа; миграции в одноразовом контейнере
   (`medusa db:migrate --execute-safe-links --all-or-nothing` из
   `/server`); только после успешной миграции `MEDUSA_TAG` в `.env`
   меняется, старый уходит в `.previous-tag`; `up -d --wait`;
   `caddy reload`; проверка `https://api.carlab.rs/health/ready`.
4. `record-medusa` двигает `deployed/medusa`, только если `deploy-medusa`
   выложила образ (`outputs.deployed == 'true'`).
5. `deploy` и `deploy-brand-site` ждут `deploy-medusa` и не стартуют, только
   если та упала.

Стек-файлы CI кладёт до `deploy.sh` и вне его lock'а: если миграция упала,
рядом со старым образом остаются новые `docker-compose.yml` и `Caddyfile`, и
следующий рестарт или откат поднимет старый образ уже с ними.

Пока не прошёл первый деплой Medusa (секреты `MEDUSA_VPS_*` появляются в
Part 3B), тега `deployed/medusa` нет, и каждый пуш в `main` собирает,
мигрирует и поднимает образ (а сайты ждут `deploy-medusa`). Это ожидаемо, а не ошибка `scope`.

### Откат

```bash
ssh deploy@<IPv4> '/srv/carlab/deploy.sh "$(cat /srv/carlab/.previous-tag)"'
```

Не запускайте эту команду дважды: откат сам переписывает `.previous-tag`
плохим sha, и второй запуск выкатит его обратно. Перед откатом запишите
хороший sha (`cat /srv/carlab/.previous-tag`).

Откатывается только образ: миграции назад не едут. Если выкат менял схему —
восстанавливать бэкап (миграции Medusa не гарантированно обратно
совместимы — старый образ против уже смигрированной вперёд схемы может не
подняться или повредить данные; см. «Что легко упустить» ниже). После
ручного отката тег `deployed/medusa` указывает на версию, которой в проде
нет; удалите его, когда исправление будет в `main`.

### Бэкап и восстановление

```bash
ssh deploy@<IPv4> /srv/carlab/backup.sh
ssh deploy@<IPv4> 'ls -la /var/backups/carlab'
ssh deploy@<IPv4> '/srv/carlab/restore.sh /var/backups/carlab/db-<stamp>.dump /var/backups/carlab/static-<stamp>.tar.gz'
```

`restore.sh` отказывается писать в базу, где уже есть таблицы, пока не задано
`RESTORE_OVER_EXISTING=yes`. На чистом сервере (DR) сначала первый деплой —
без `MEDUSA_TAG` в `.env` compose не поднимется, — и только потом
`RESTORE_OVER_EXISTING=yes /srv/carlab/restore.sh …` поверх пустой смигрированной
базы. `backup.sh` берёт тот же `.deploy.lock`, что и `deploy.sh`: если в 03:30
идёт деплой, бэкап пропускается с ненулевым кодом и строкой в
`/var/log/carlab-backup.log`. Сиды, миграции и создание админа — только из
образа (`docker compose exec -T medusa node_modules/.bin/medusa …`,
скрипты — `./src/scripts/<name>.js`), никогда из чекаута репозитория: в
образе нет ts-node.

### Локальная проверка стека

Тот же compose поднимается на своей машине без отдельного override —
через переменные в `infra/medusa/.env` (он в `.gitignore`):
`API_HOST=localhost`, `HTTP_PORT=8080`, `HTTPS_PORT=8443`,
`MEDUSA_IMAGE=podbor-medusa`, `MEDUSA_TAG=local` плюс секреты; образ —
`docker build -f infra/medusa/Dockerfile -t podbor-medusa:local .`. Проверка —
`curl -k https://localhost:8443/health/ready`.

### Что легко упустить

- **`.env` читается буквально.** `deploy.sh` вытаскивает значения из `.env`
  через `sed`, без снятия кавычек — не оборачивайте значения в `"…"`,
  кавычки попадут в само значение.
- **`umask 077` на сервере.** `deploy.sh` и `backup.sh` ставят его сами:
  `.env` и файлы бэкапа в `/var/backups/carlab` ложатся с правами 600/700 и
  владельцем `deploy`.
- **Откат — это только образ.** `deploy.sh <предыдущий_sha>` поднимает старый
  код против схемы, которую мог уже смигрировать вперёд новый образ; миграции
  Medusa не гарантированно обратно совместимы. Если откатываемый деплой менял
  схему — старый образ может не стартовать или повредить данные; в этом
  случае откат — это восстановление бэкапа, снятого перед деплоем, а не
  `deploy.sh` со старым тегом.
- **Порт наружу даёт только Caddy.** `ports:` в docker compose обходит ufw —
  правило фильтрует трафик на хосте, а не то, что Docker сам пробрасывает
  через iptables. Никогда не добавляйте `ports:` другим сервисам compose-стека.
- **Docker apt-ключ не сверен по отпечатку.** `bootstrap-host.sh` не пинит
  fingerprint GPG-ключа Docker — его нет на странице установки Docker для
  Ubuntu. После бутстрапа сверьте вручную:
  `gpg --show-keys /etc/apt/keyrings/docker.asc` — и сравните с отпечатком,
  который публикует сама документация Docker (не переписывайте его сюда).
- **Ключ CI — фактически root.** `deploy` состоит в группе `docker` (и имеет
  `NOPASSWD` sudo); группа `docker` сама по себе равна root, так что `restrict`
  в `authorized_keys` ограничивает только форвардинг/pty. Принятый риск.
- **`ufw limit 22/tcp`** пускает не больше 6 новых соединений за 30 секунд с
  одного адреса. `deploy-medusa` за один прогон открывает 4 ssh-соединения к
  серверу (заливка стек-файлов, логин в GHCR, запуск `deploy.sh`, логаут) —
  запас есть, но не добавляйте ssh-вызовы в этот шаг бездумно.
- **Cron бэкапа — в таймзоне хоста**, на образах Hetzner это UTC: `03:30 UTC`
  выше и есть местное время сервера. `/var/log/carlab-backup.log` растёт без
  ограничения — добавьте logrotate-сниппет вручную (в репозиторий его никто
  не кладёт):
  ```
  /var/log/carlab-backup.log {
    weekly
    rotate 8
    compress
    missingok
    notifempty
  }
  ```
- **Ubuntu 24.04 запускает ssh через socket activation** — `systemctl reload
ssh` после `harden-ssh.sh` может отчитаться не так, как ожидается. Прежде чем
  закрывать первую сессию, откройте второй терминал и убедитесь, что вход по
  ключу под `deploy` по-прежнему работает.
- **У Caddy пока нет CSP** — `caddy/Caddyfile` ставит HSTS, `X-Content-Type-Options`,
  `Referrer-Policy`, `X-Frame-Options`, снимает `Server`, но Content-Security-Policy
  не задан. Единственное ограничение на загрузку в админку — `request_body`
  `max_size 25MB` в том же Caddyfile.
- **Правка `pnpm-lock.yaml` передеплоивает и Medusa** — один lockfile на все
  четыре приложения, `scope` не умеет приписать его правку одному из них
  (см. «Корневые файлы проверяются отдельным `git diff`» выше). Решение
  осознанное: лишний деплой дешевле пропущенного.

### Первый выкат — чеклист

> Чек-лист для человека-владельца инфраструктуры. Каждый шаг — конкретная
> команда и условие «готово». Агент этот раздел не выполняет — здесь описаны
> только шаги, которые нужно проделать руками вне репозитория (Hetzner
> Console, DNS у регистратора, Brevo, GitHub Secrets).

1. **Hetzner.** В Console проверить доступность CX23 (запасной вариант —
   CPX22) и цену автобэкапа в нужном регионе. Создать сервер: Ubuntu 24.04,
   IPv4 + IPv6, автобэкапы включены.
   Готово: сервер виден в Console, есть оба адреса.
2. **Bootstrap.** Зайти по root/ssh-ключу, залить на сервер
   `infra/medusa/bootstrap-host.sh` и `infra/medusa/harden-ssh.sh`, запустить
   `bootstrap-host.sh`. Открыть отдельную интерактивную сессию
   `ssh deploy@<IPv4>` и **не закрывать её**, пока вход по ключу не будет
   перепроверен после hardening. Из неё **через `sudo`** запустить
   `harden-ssh.sh`.
   Готово: `ssh deploy@<IPv4>` пускает по ключу без пароля; `ssh root@<IPv4>`
   отказывает.
3. **DNS.** Прописать A- и AAAA-записи `api.carlab.rs` на IPv4/IPv6 сервера.
   Проверить IPv6 отдельно: `curl -6 https://api.carlab.rs/health/ready` (пока
   не задеплоено — на этом шаге просто резолвится). Если IPv6 недоступен у
   хостера/сети — AAAA-запись убрать. После первого деплоя (шаг 8) с машины
   с IPv6 открыть соединение и держать его:
   `openssl s_client -6 -connect api.carlab.rs:443 -servername api.carlab.rs`.
   Пока оно открыто, на сервере в `/srv/carlab`:
   `sudo nsenter -n -t "$(docker inspect -f '{{.State.Pid}}' "$(docker compose ps -q caddy)")" ss -tn '( sport = :443 )'`
   — в колонке Peer должен стоять глобальный IPv6-адрес клиента, а не
   `fd00:ca7:1ab::1` или IPv4 шлюза docker. Access-лога у Caddy нет, поэтому
   проверка по сокету.
   Готово: `dig +short api.carlab.rs` и `dig +short AAAA api.carlab.rs`
   отдают адреса сервера.
4. **Brevo.** Подтвердить домен `carlab.rs` (DKIM + DMARC), выпустить
   API-ключ, завести отправителя на этом домене.
   Готово: домен в Brevo помечен verified, есть API-ключ и адрес отправителя.
5. **Токены.** Создать fine-grained PAT для `GITHUB_DISPATCH_TOKEN`
   (только этот репозиторий, Actions: Read and write) и ключ OpenAI.
   Готово: оба значения сохранены в менеджере паролей (пока не в GitHub —
   это шаг 7).
6. **`.env` на сервере.** Скопировать `infra/medusa/production.env.example`
   в `/srv/carlab/.env`, заполнить все значения (пароли — `openssl rand -hex
32`), `chmod 600 /srv/carlab/.env`.
   Готово: `ssh deploy@<IPv4> 'stat -c %a /srv/carlab/.env'` печатает `600`.
7. **Секреты CI.** Сгенерировать ssh-ключ CI (`ssh-keygen -t ed25519`),
   ограничить публичную часть на сервере (`restrict` в `authorized_keys`),
   получить `known_hosts` (`ssh-keyscan -t ed25519 <IPv4>`) и **сверить
   отпечаток** отдельно (например, при первом интерактивном
   `ssh deploy@<IPv4>`). Записать `MEDUSA_VPS_USER`, `MEDUSA_VPS_SSH_KEY`,
   `MEDUSA_VPS_KNOWN_HOSTS` в секреты **репозитория** и переменную
   `MEDUSA_URL` в GitHub Variables; `MEDUSA_VPS_HOST` — **последним**: с ним
   следующий пуш в `main` уже деплоит.
   Готово: все четыре секрета и переменная видны в Settings → Secrets and
   variables → Actions.
8. **Первый деплой.** Запустить `ci.yml` (пуш в `main` или
   `workflow_dispatch`). Проверить пакет в GHCR: привязан к репозиторию,
   видимость и доступ Actions на чтение настроены.
   Готово: `deploy-medusa` зелёная, джоба `record-medusa` передвинула тег
   `deployed/medusa`,
   `https://api.carlab.rs/health/ready` отвечает 200.
9. **Данные.** Прогнать сиды `seed-base.js`, `seed-batteries.js`
   (`docker compose exec -T medusa node_modules/.bin/medusa exec
./src/scripts/seed-base.js`, аналогично для второго). Создать админа
   (`medusa user --invite`). В админке скопировать publishable key, который
   создал `seed-base.js` (новый не выпускать), в секрет
   `MEDUSA_PUBLISHABLE_KEY`.
   Готово: вход в `/app` под новым админом работает, `MEDUSA_PUBLISHABLE_KEY`
   в секретах.
10. **Приёмка.** `/health/ready` отвечает 200; тестовый заказ через Store API
    (вебхук заказа выключен — Plan 4); письмо клиенту дошло; `docker stats
--no-stream` под небольшой нагрузкой укладывается в лимиты памяти; ручной

    `/var/log/carlab-backup.log` на сервере, что cron отработал.
    Готово: все пункты пройдены, дата и результат записаны рядом с этим

## Автоперевод контента

Кейсы (`src/content/cases`, `works`,
`products`) и UI-копия (`src/content/i18n/*.yaml`) переводятся автоматически.
Админ в Keystatic пишет только русские поля — ни один из четырёх языков в
`translations` там не обязателен, потому что Keystatic не умеет запускать
API-вызов из своей формы, так что кнопки «Перевести» там в принципе быть не
может.

Вместо неё — джоба `translate` в `.github/workflows/ci.yml`: при каждом пуше
(**в любую ветку**, не только `main`) она проходит по всем `apps/*/` и
прогоняет каждый найденный скрипт (`translate-cases`, `translate-works`,
`translate-i18n`), после чего коммитит результат обратно — так переводы уже
есть в фиче-ветке к моменту мержа, а не появляются только после него.

Это безопасно гонять на всех ветках: `git.deploymentEnabled` теперь `false`
целиком, Vercel больше не деплоит по git-пушу ни для одной ветки — коммит с
переводом на фиче-ветке в принципе не может запустить лишний билд. На `main`
деплой-джобы идут следом за `translate` в том же прогоне и чекаутят именно
тот коммит, который она оставила после себя, — но выкатывается из них только
то, что отстало от прода (см. «Деплоится не всё подряд»). Сам шаг `translate`
при этом безусловный: он один на все три приложения и гоняется на каждом
пуше, потому что каждая строка сначала ищется в кэше — прогон, которому нечего
переводить, не делает ни одного запроса к OpenAI.

Единица работы — одна строка, а не файл. Рядом с контентом лежит
`apps/<app>/src/content/translations.cache.json`: кэш, ключом которого служит
тройка «системный промпт + модель + русская строка». Поэтому правка одного предложения
отправляет модели одно предложение, а не весь файл со всеми локалями.

Файла в репозитории пока нет — его создаёт первый прогон `translate` на этой
ветке. Ключ кэша — путь файла, поэтому переименование каталога кейса теряет его
блок, и следующий прогон усыновляет лежащие в файле переводы как рукописные:
этот файл молча выпадает из ближайшей правки промпта.

**Этот файл обязан быть закоммичен.** Его удаление стоит полной перегенерации
корпуса по прайсу OpenAI — примерно 112 тысяч символов на локаль. Правка
промпта или смена модели меняют отпечаток и перегенерируют всё, что этот
промпт произвёл: это единственный штатный способ применить исправленный
промпт к уже переведённому тексту.

`translatedFrom` остался: он хранит хеш всего русского источника и отвечает на
вопрос «сделаны ли лежащие рядом переводы из того русского, что в файле
сейчас». От этого ответа зависит, будет ли принята ручная правка перевода —
и хеш считается по **всему** файлу, поэтому правка любой русской строки
отбрасывает все ручные переводы в этом файле, а не только соседний. В лог как
`overwriting hand-written <path>` попадают те, чей собственный русский не
менялся; строка, русский которой вы и правили, заменяется молча — под новым
ключом в кэше сравнивать не с чем.

Без `OPENAI_API_KEY` джоба падает на шаге перевода — существующий контент это
не затронет, только новые/изменённые тексты останутся без перевода до
следующего успешного запуска. Ручной прогон — обязательно изнутри приложения (скрипты ищут контент
относительно текущей директории). Режима dry-run нет: скрипт ходит в OpenAI и
переписывает контент, `translatedFrom` и кэш, так что локально его запускают
только чтобы отладить сам скрипт:

```bash
cd apps/approved-rs
node --env-file=.env --experimental-strip-types scripts/translate-cases.ts
```

## Telegram webhook (только approved.rs)

Группа получает только короткий тизер заявки («#123 · Иван · Автоподбор ·
статус») и кнопку-ссылку «Открыть в боте» — всё управление (статусы,
редактирование, архив, деньги) происходит в личке с ботом. Заявки хранятся
в Vercel Blob (`data/leads.json`, приватный доступ), без внешней БД.

Владелец и админ должны один раз написать боту `/start`, прежде чем бот
сможет слать им личные сообщения (в т.ч. напоминания по крону) — Telegram
запрещает боту начинать переписку первым.

Webhook регистрируется **один раз на бота**, и указывает на approved.rs:
у carlab.rs и details.rs роута `/api/telegram-webhook` просто нет. Обязательно
с `secret_token`, равным `TELEGRAM_WEBHOOK_SECRET` проекта approved.rs — без
совпадения эндпоинт отвечает 401 на любой запрос:

```bash
curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook?url=https://approved.rs/api/telegram-webhook&secret_token=<TELEGRAM_WEBHOOK_SECRET>"
```

Проверить:

```bash
curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getWebhookInfo"
```

То же самое делает `apps/approved-rs/scripts/register-webhook.ts`, читая
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` и `SITE` из окружения:

```bash
cd apps/approved-rs
node --env-file=.env.local --experimental-strip-types scripts/register-webhook.ts
```

> боту и ответы на его промпты про суммы сделок до вебхука не доходили. Если
> вебхук регистрировали им раньше — перерегистрируйте.

## Cron напоминаний (только approved.rs)

`apps/approved-rs/vercel.json`:

```json
"crons": [{ "path": "/api/reminders", "schedule": "0 8 * * *" }]
```

Каждый день в 08:00 UTC Vercel дёргает `/api/reminders`, подставляя
`Authorization: Bearer $CRON_SECRET` — роут разбирает отложенные («напомни
мне») заявки, у которых подошёл срок, и возвращает их владельцу. Без
`CRON_SECRET` в проекте роут отвечает 401, и напоминания молча не приходят.

Cron привязан к проекту, а не к боту: у двух других проектов секции `crons`
в `vercel.json` нет, добавлять её не нужно — иначе одни и те же напоминания
уедут по несколько раз.

## Pnpm на Vercel

Реальный деплой (`git push origin main` → `ci.yml`) этого вообще не касается:
`vercel build`/`vercel deploy` запускаются из GitHub Actions, где
`pnpm/action-setup` уже поставил pnpm из `packageManager` в корневом
`package.json` (сейчас 11.22.0) — `vercel build` выполняет
`installCommand`/`buildCommand` тем же процессом, а не в отдельном
Vercel-контейнере со своей версией pnpm.

Ниже актуально только для ручного деплоя из дашборда Vercel (кнопка
Redeploy) или git-триггера, если `git.deploymentEnabled` когда-нибудь снова
включат — в обоих случаях сборку выполняет сам Vercel:

- Vercel определяет версию pnpm по `lockfileVersion` в `pnpm-lock.yaml`
- pnpm v11 официально им не поддерживается (максимум — 10)

Поэтому `pnpm-workspace.yaml` держит список разрешённых сборок дважды, в
формате обеих версий:

```yaml
packages:
  - 'apps/*'
  - 'packages/*'

allowBuilds: # pnpm v11
  esbuild: true
  sharp: true
  '@parcel/watcher': true

onlyBuiltDependencies: # pnpm v9/v10 (Vercel)
  - esbuild
  - sharp
  - '@parcel/watcher'
```
